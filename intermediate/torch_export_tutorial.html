PyTorch.export 教程 ¶


创建于：2025 年 4 月 1 日 | 最后更新：2025 年 4 月 1 日 | 最后验证：2024 年 11 月 5 日

作者：威廉·文，陈正旭，叶安嘉，帕瓦卡潘

警告

torch.export 及其相关功能处于原型状态，可能破坏向后兼容性。本教程提供了 PyTorch 2.5 中 torch.export 使用情况的快照。

torch.export() 是将 PyTorch 模型导出为标准模型表示的方法，旨在在不同的（即无 Python 环境）环境中运行。官方文档可在此处找到。

在本教程中，您将学习如何使用 torch.export() 从 PyTorch 程序中提取 ExportedProgram （即单图表示）。我们还详细说明了您可能需要进行的考虑/修改，以便使您的模型与 torch.export 兼容。

基本用法

torch.export 通过跟踪目标函数并给定示例输入，从 PyTorch 程序中提取单图表示。 torch.export.export() 是 torch.export 的主入口点。

在本教程中， torch.export 和 torch.export.export() 实际上同义，尽管 torch.export 通常指 PyTorch 2.X 导出过程，而 torch.export.export() 通常指实际函数调用。

torch.export.export() 的签名是：

export(
    mod: torch.nn.Module,
    args: Tuple[Any, ...],
    kwargs: Optional[Dict[str, Any]] = None,
    *,
    dynamic_shapes: Optional[Dict[str, Dict[int, Dim]]] = None
) -> ExportedProgram

从调用 mod(*args, **kwargs) 跟踪张量计算图，并用 ExportedProgram 包装，以便稍后可以不同输入进行序列化或执行。要执行 ExportedProgram ，我们可以调用其上的 .module() 来返回一个可调用的对象，就像原始程序一样。我们将在教程中稍后详细介绍 dynamic_shapes 参数。

import torch
from torch.export import export

class MyModule(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.lin = torch.nn.Linear(100, 10)

    def forward(self, x, y):
        return torch.nn.functional.relu(self.lin(x + y), inplace=True)

mod = MyModule()
exported_mod = export(mod, (torch.randn(8, 100), torch.randn(8, 100)))
print(type(exported_mod))
print(exported_mod.module()(torch.randn(8, 100), torch.randn(8, 100)))

让我们回顾一下 ExportedProgram 的某些有趣属性。

graph 属性是从我们导出的函数中追踪的 FX 图，即所有 PyTorch 操作的计算图。FX 图是“ATen IR”格式，意味着它只包含“ATen 级”操作。

graph_signature 属性提供了对导出图中输入和输出节点的更详细描述，说明哪些是参数、缓冲区、用户输入或用户输出。

range_constraints 属性将在稍后介绍。

print(exported_mod)

请参阅 torch.export 文档以获取更多详细信息。

图断开 ¶

虽然 torch.export 与 torch.compile 具有共享组件，但 torch.export 的关键限制，尤其是在与 torch.compile 相比时，是它不支持图形中断。这是因为处理图形中断涉及将不支持的操作解释为默认的 Python 评估，这与导出用例不兼容。因此，为了使您的模型代码与 torch.export 兼容，您需要修改代码以删除图形中断。

在以下情况下需要图形中断：

  • 数据依赖的控制流

class Bad1(torch.nn.Module):
    def forward(self, x):
        if x.sum() > 0:
            return torch.sin(x)
        return torch.cos(x)

import traceback as tb
try:
    export(Bad1(), (torch.randn(3, 3),))
except Exception:
    tb.print_exc()

  • 使用 .data 访问张量数据

class Bad2(torch.nn.Module):
    def forward(self, x):
        x.data[0, 0] = 3
        return x

try:
    export(Bad2(), (torch.randn(3, 3),))
except Exception:
    tb.print_exc()

  • 调用不受支持的函数（例如许多内置函数）

class Bad3(torch.nn.Module):
    def forward(self, x):
        x = x + 1
        return x + id(x)

try:
    export(Bad3(), (torch.randn(3, 3),))
except Exception:
    tb.print_exc()

非严格导出 ¶

为了追踪程序，默认使用 TorchDynamo，一个字节码分析引擎，对 Python 代码进行符号分析并基于结果构建图。这种分析允许提供更强大的安全性保证，但并非所有 Python 代码都受支持，导致这些图断裂。

为了解决这个问题，在 PyTorch 2.3 中，我们引入了一种新的导出模式，称为非严格模式，其中我们使用 Python 解释器跟踪程序，执行方式与在急切模式中完全相同，允许我们跳过不受支持的 Python 特性。这是通过添加 strict=False 标志来实现的。

看一些之前导致图断裂的例子：

  • 调用不受支持的函数（如许多内置函数）会追踪

通过，但在此情况下， id(x) 在图中被专门化为一个常量整数。这是因为 id(x) 不是一个张量操作，所以该操作没有记录在图中。

class Bad3(torch.nn.Module):
    def forward(self, x):
        x = x + 1
        return x + id(x)

bad3_nonstrict = export(Bad3(), (torch.randn(3, 3),), strict=False)
print(bad3_nonstrict)
print(bad3_nonstrict.module()(torch.ones(3, 3)))

然而，还有一些功能需要重写原始模块：

控制流操作

实际上确实支持数据依赖的控制流。但这些需要使用控制流操作来表示。例如，我们可以使用 cond 操作符来修复上面的控制流示例，如下所示：

class Bad1Fixed(torch.nn.Module):
    def forward(self, x):
        def true_fn(x):
            return torch.sin(x)
        def false_fn(x):
            return torch.cos(x)
        return torch.cond(x.sum() > 0, true_fn, false_fn, [x])

exported_bad1_fixed = export(Bad1Fixed(), (torch.randn(3, 3),))
print(exported_bad1_fixed)
print(exported_bad1_fixed.module()(torch.ones(3, 3)))
print(exported_bad1_fixed.module()(-torch.ones(3, 3)))

cond 存在一些限制，应该引起注意：

  • 断言（即 x.sum() > 0 ）必须返回布尔值或单元素张量。

  • 操作数（即 [x] ）必须是张量。

  • 分支函数（即 true_fn 和 false_fn ）的签名必须与操作数匹配，并且它们都必须返回具有相同元数据的单个张量（例如， dtype 、 shape 等）。

  • 分支函数不能修改输入或全局变量。

  • 分支函数不能访问闭包变量，除非函数是在方法作用域内定义的，此时可以访问 self 。

想了解更多关于 cond 的信息，请查看 cond 文档。

我们还可以使用 map ，它应用于第一个张量参数的第一维。

from torch._higher_order_ops.map import map as torch_map

class MapModule(torch.nn.Module):
    def forward(self, xs, y, z):
        def body(x, y, z):
            return x + y + z

        return torch_map(body, xs, y, z)

inps = (torch.ones(6, 4), torch.tensor(5), torch.tensor(4))
exported_map_example = export(MapModule(), inps)
print(exported_map_example)
print(exported_map_example.module()(*inps))

其他控制流操作包括 while_loop ， associative_scan 和 scan 。有关每个操作器的更多文档，请参阅此页面。

约束/动态形状

本节涵盖了导出程序的动态行为和表示。动态行为取决于导出的特定模型，因此在本教程的大部分内容中，我们将关注这个特定的玩具模型（结果张量形状已标注）：

class DynamicModel(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.l = torch.nn.Linear(5, 3)

    def forward(
        self,
        w: torch.Tensor,  # [6, 5]
        x: torch.Tensor,  # [4]
        y: torch.Tensor,  # [8, 4]
        z: torch.Tensor,  # [32]
    ):
        x0 = x + y  # [8, 4]
        x1 = self.l(w)  # [6, 3]
        x2 = x0.flatten()  # [32]
        x3 = x2 + z  # [32]
        return x1, x3

默认情况下， torch.export 生成一个静态程序。其后果之一是，即使在急切模式下有效，程序在运行时也无法处理不同形状的输入。

w = torch.randn(6, 5)
x = torch.randn(4)
y = torch.randn(8, 4)
z = torch.randn(32)
model = DynamicModel()
ep = export(model, (w, x, y, z))
model(w, x, torch.randn(3, 4), torch.randn(12))
try:
    ep.module()(w, x, torch.randn(3, 4), torch.randn(12))
except Exception:
    tb.print_exc()

基本概念：符号和守卫

要启用动态性， export() 提供了一个 dynamic_shapes 参数。处理动态形状的最简单方法是使用 Dim.AUTO 并查看返回的程序。动态行为是在输入维度级别指定的；对于每个输入，我们可以指定一个值元组：

from torch.export.dynamic_shapes import Dim

dynamic_shapes = {
    "w": (Dim.AUTO, Dim.AUTO),
    "x": (Dim.AUTO,),
    "y": (Dim.AUTO, Dim.AUTO),
    "z": (Dim.AUTO,),
}
ep = export(model, (w, x, y, z), dynamic_shapes=dynamic_shapes)

在我们查看生成的程序之前，让我们了解指定 dynamic_shapes 的含义以及它与导出的交互。对于每个指定了 Dim 对象的输入维度，都会分配一个符号，该符号承担一个 [2, inf] 范围（为什么不 [0, inf] 或 [1, inf] ？我们将在 0/1 专业化部分稍后解释）。

然后运行模型跟踪，查看模型执行的每个操作。每个单独的操作可以发出所谓的“守卫”；基本上是程序有效的布尔条件。当守卫涉及为输入维度分配的符号时，程序包含对有效输入形状的限制；即程序的动态行为。符号形状子系统是负责接收所有发出的守卫并生成遵循所有这些守卫的最终程序表示的部分。在我们看到这个“最终表示”之前，先看看我们正在跟踪的玩具模型发出的守卫。

在这里，每个正向输入张量都标注了跟踪开始时分配的符号：

class DynamicModel(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.l = torch.nn.Linear(5, 3)

    def forward(
        self,
        w: torch.Tensor,  # [s0, s1]
        x: torch.Tensor,  # [s2]
        y: torch.Tensor,  # [s3, s4]
        z: torch.Tensor,  # [s5]
    ):
        x0 = x + y  # guard: s2 == s4
        x1 = self.l(w)  # guard: s1 == 5
        x2 = x0.flatten()  # no guard added here
        x3 = x2 + z  # guard: s3 * s4 == s5
        return x1, x3

让我们理解每个操作和发出的守卫：

  • x0 = x + y ：这是一个逐元素加法，具有广播功能，因为 x 是一个一维张量，而 y 是一个二维张量。 x 沿着 y 的最后一个维度进行广播，发出守卫 s2 == s4 。

  • x1 = self.l(w) : 调用 nn.Linear() 执行模型参数的矩阵乘法。在导出时，参数、缓冲区和常量被视为程序状态，这被认为是静态的，因此这是一个动态输入（ w: [s0, s1] ）和静态形状张量之间的矩阵乘法。这会发出保护器 s1 == 5 。

  • x2 = x0.flatten() : 这个调用实际上没有发出任何保护器！（至少与输入形状相关的没有）

  • x3 = x2 + z : x2 在展平后具有形状 [s3*s4] ，这个逐元素加法会发出 s3 * s4 == s5 。

将所有这些保护器写下来并总结，几乎就像一个数学证明，这正是符号形状子系统试图做的事情！总之，我们可以得出结论，程序必须具有以下输入形状才是有效的：

  • w: [s0, 5]

  • x: [s2]

  • y: [s3, s2]

  • z: [s2*s3]

当我们最终打印出导出的程序以查看结果时，我们看到的是对应输入上标注的这些形状：

print(ep)

另一个需要注意的特性是上面的 range_constraints 字段，它包含每个符号的有效范围。目前这并不那么有趣，因为这个导出调用不会发出与符号边界相关的任何守卫，每个基本符号都有一个通用的边界，但这一点将在稍后出现。

到目前为止，因为我们一直在导出这个玩具模型，所以这种体验并不能代表调试动态形状守卫和问题通常有多困难。在大多数情况下，并不明显哪些守卫被发出，哪些操作和用户代码的部分负责。对于这个玩具模型，我们能够精确地定位到具体的行，守卫也比较直观。

在更复杂的情况下，一个有帮助的第一步总是启用详细日志记录。这可以通过环境变量 TORCH_LOGS="+dynamic" 完成，或者通过 torch._logging.set_logs(dynamic=10) 交互式地完成：

torch._logging.set_logs(dynamic=10)
ep = export(model, (w, x, y, z), dynamic_shapes=dynamic_shapes)

即使是这样一个简单的玩具模型，输出的信息量也相当大。这里为了忽略不必要的日志信息，将日志的前后部分进行了截断，但通过查看日志，我们可以看到与我们上述描述相关的行；例如，符号的分配：

在 [guard added] 消息旁边，我们还可以看到负责的用户代码行 - 幸运的是这里的模型足够简单。在许多现实世界的案例中，情况并不那么简单：高级 torch 操作可能有复杂的虚拟内核实现或算子分解，这会使得守卫的生成位置和内容变得复杂。在这种情况下，最好的方法是按照日志的建议深入调查，并使用环境变量 TORCHDYNAMO_EXTENDED_DEBUG_GUARD_ADDED="..." 重新运行，以进一步追踪感兴趣的守卫。

Dim.AUTO 只是与 dynamic_shapes 交互的可用选项之一；截至本文撰写时，还有 2 个其他选项可用： Dim.DYNAMIC 和 Dim.STATIC 。 Dim.STATIC 简单地标记一个维度为静态，而 Dim.DYNAMIC 在所有方面都与 Dim.AUTO 相似，只有一个区别：当专门化到常量时会引发错误；这是为了保持动态性。例如，当在动态标记的维度上发出静态守卫时，看看会发生什么：

dynamic_shapes["w"] = (Dim.AUTO, Dim.DYNAMIC)
try:
    export(model, (w, x, y, z), dynamic_shapes=dynamic_shapes)
except Exception:
    tb.print_exc()

静态守卫也不一定固有于模型；它们也可以来自用户指定。事实上，导致形状专业化的常见陷阱之一是用户为等效维度指定了冲突的标记；一个是动态的，另一个是静态的。当这种情况发生在 x.shape[0] 和 y.shape[1] 时，会引发相同的错误类型：

dynamic_shapes["w"] = (Dim.AUTO, Dim.AUTO)
dynamic_shapes["x"] = (Dim.STATIC,)
dynamic_shapes["y"] = (Dim.AUTO, Dim.DYNAMIC)
try:
    export(model, (w, x, y, z), dynamic_shapes=dynamic_shapes)
except Exception:
    tb.print_exc()

你可能会问为什么“导出”会“专业化”，即为什么我们通过选择静态路径来解决这种静态/动态冲突。答案是，因为上述符号形状系统，包括符号和守卫。当 x.shape[0] 被标记为静态时，我们不分配符号，并编译将此形状视为具体的整数 4。为 y.shape[1] 分配符号，所以我们最终发出守卫 s3 == 4 ，导致专业化。

导出功能的一个特点是，在跟踪过程中，断言、 torch._check() 和 if/else 条件语句也会发出守卫。看看当我们用这样的语句增强现有模型时会发生什么：

class DynamicModel(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.l = torch.nn.Linear(5, 3)

    def forward(self, w, x, y, z):
        assert w.shape[0] <= 512
        torch._check(x.shape[0] >= 4)
        if w.shape[0] == x.shape[0] + 2:
            x0 = x + y
            x1 = self.l(w)
            x2 = x0.flatten()
            x3 = x2 + z
            return x1, x3
        else:
            return w

dynamic_shapes = {
    "w": (Dim.AUTO, Dim.AUTO),
    "x": (Dim.AUTO,),
    "y": (Dim.AUTO, Dim.AUTO),
    "z": (Dim.AUTO,),
}
try:
    ep = export(DynamicModel(), (w, x, y, z), dynamic_shapes=dynamic_shapes)
except Exception:
    tb.print_exc()

这些语句中的每一个都会发出一个额外的守卫，导出的程序显示了这些变化； s0 被消除，以 s2 + 2 代替，而 s2 现在包含上下界，反映在 range_constraints 中。

对于 if/else 条件，你可能会问为什么选择了 True 分支，以及为什么不是从跟踪中发出的 w.shape[0] != x.shape[0] + 2 守卫。答案是，导出是由跟踪提供的样本输入引导的，并针对所选择的分支进行优化。如果提供了不同的样本输入形状，这些输入会失败 if 条件，导出将跟踪并发出对应于 else 分支的守卫。此外，你可能会问为什么只跟踪了 if 分支，以及是否可能保持程序中的控制流并保持两个分支都活跃。关于这一点，请参考上面的 Control Flow Ops 部分，重新编写你的模型代码。

0/1 专业方向 ¶

既然我们在谈论守卫和特殊化，那么讨论我们之前提到的 0/1 特殊化问题是个好时机。关键是导出将专门针对值为 0 或 1 的样本输入维度，因为这些形状的跟踪时间属性不能推广到其他形状。例如，大小为 1 的张量可以广播，而其他大小的张量则不行；大小为 0……这仅仅意味着当你想让你的程序硬编码样本输入时，你应该指定 0/1 样本输入，而当需要动态行为时，则指定非 0/1 样本输入。看看当我们导出这个线性层时运行时会发生什么：

ep = export(
    torch.nn.Linear(4, 3),
    (torch.randn(1, 4),),
    dynamic_shapes={
        "input": (Dim.AUTO, Dim.STATIC),
    },
)
try:
    ep.module()(torch.randn(2, 4))
except Exception:
    tb.print_exc()

命名维度 ¶

截至目前，我们只讨论了 3 种指定动态形状的方法： Dim.AUTO 、 Dim.DYNAMIC 和 Dim.STATIC 。这些方法的吸引力在于低摩擦的用户体验；在模型追踪过程中发出的所有守卫都得到遵守，并且最小/最大范围、关系以及静态/动态维度等动态行为在导出过程中自动确定。动态形状子系统本质上充当一个“发现”过程，总结这些守卫，并展示导出认为的程序的整体动态行为。这种设计的缺点在于，一旦用户对这些模型的动态行为有更强的期望或信念——可能对动态性有强烈的渴望，并且不惜一切代价避免对特定维度的专业化，或者可能我们只想通过原始模型代码的变化来捕捉动态行为的变化，或者可能是底层分解或元核的变化。这些变化不会被检测到，除非有测试来检查结果 ExportedProgram 表示。

对于此类情况，我们建议采用“传统”方式指定动态形状，这可能为长期使用导出的用户所熟悉：使用命名 Dims ：

dx = Dim("dx", min=4, max=256)
dh = Dim("dh", max=512)
dynamic_shapes = {
    "x": (dx, None),
    "y": (2 * dx, dh),
}

这种动态形状的风格允许用户指定哪些符号分配给输入维度，这些符号的最小/最大边界，并对 ExportedProgram 的动态行为施加限制；如果模型跟踪生成与关系或静态/动态指定冲突的守卫，将引发 ConstraintViolation 错误。例如，在上面的指定中，以下内容被断言：

  • x.shape[0] 应具有范围 [4, 256] ，并通过 y.shape[0] == 2 * x.shape[0] 与 y.shape[0] 相关联。

  • x.shape[1] 是静态的。

  • y.shape[1] 具有范围 [2, 512] ，且与任何其他维度无关。

在本设计中，我们允许使用一元线性表达式指定维度之间的关系： A * dim + B 可以用于任何维度。这使用户能够指定更复杂的约束，例如动态维度的整数可除性：

dx = Dim("dx", min=4, max=512)
dynamic_shapes = {
    "x": (4 * dx, None)  # x.shape[0] has range [16, 2048], and is divisible by 4.
}

约束违规，建议的修复方法 ¶

在引入 Dim.AUTO 之前，这种规范风格（规范经常与模型跟踪产生的结果不匹配）的一个常见问题是，这会导致 ConstraintViolation 错误和导出建议的修复方案 - 例如，在这个模型和规范中，模型内在地要求 x 和 y 的维度 0 之间相等，并要求维度 1 为静态。

class Foo(torch.nn.Module):
    def forward(self, x, y):
        w = x + y
        return w + torch.ones(4)

dx, dy, d1 = torch.export.dims("dx", "dy", "d1")
try:
    ep = export(
        Foo(),
        (torch.randn(6, 4), torch.randn(6, 4)),
        dynamic_shapes={
            "x": (dx, d1),
            "y": (dy, d1),
        },
    )
except Exception:
    tb.print_exc()

预期与建议的修复方案是，用户可以交互式地将更改复制粘贴到他们的动态形状规范中，并在之后成功导出。

最后，关于规范选项还有一些值得了解的知识点：

  • None 是静态行为的一个好选项：- dynamic_shapes=None （默认）导出时整个模型是静态的。- 在输入级别指定 None 将导出所有张量维度为静态，并且对于非张量输入也是必需的。- 在维度级别指定 None 将专门化该维度，尽管这已被 Dim.STATIC 取代。

  • 指定每个维度的整数值也会产生静态行为，并且还会检查提供的样本输入是否与规范匹配。

以下选项在下面的输入和动态形状规范中进行了组合：

inputs = (
    torch.randn(4, 4),
    torch.randn(3, 3),
    16,
    False,
)
dynamic_shapes = {
    "tensor_0": (Dim.AUTO, None),
    "tensor_1": None,
    "int_val": None,
    "bool_val": None,
}

数据相关错误 ¶

在尝试导出模型时，您可能遇到了“无法在数据相关表达式中进行保护”或“无法从数据相关表达式中提取专用整数”之类的错误。这些错误存在的原因是 torch.export() 使用 FakeTensors 编译程序，这些 FakeTensors 以符号形式表示它们的真实张量对应物。虽然它们具有等效的符号属性（例如大小、步长、数据类型），但它们在 FakeTensors 不包含任何数据值方面存在差异。这避免了不必要的内存使用和昂贵的计算，但这也意味着导出可能无法直接编译用户代码的部分，其中编译依赖于数据值。简而言之，如果编译器需要具体的、数据相关的值才能继续，它将报错，抱怨该值不可用。

数据依赖的值出现在许多地方，常见的来源是像 item() 、 tolist() 或 torch.unbind() 这样的调用，它们从张量中提取标量值。这些值在导出的程序中是如何表示的呢？在“约束/动态形状”部分，我们讨论了为表示动态输入维度分配符号。这里也是同样的情况：我们为程序中出现的每个数据依赖值分配符号。重要的是，这些是“无后盾”的符号，与为输入维度分配的“有后盾”符号形成对比。“有后盾/无后盾”的命名法指的是符号是否存在“提示”：一个支持符号的具体值，可以告知编译器如何进行操作。

在输入形状符号的情况（有后盾符号）中，这些提示仅仅是提供的样本输入形状，这就是为什么控制流分支是由样本输入属性决定的。对于数据依赖值，符号是在跟踪过程中从 FakeTensor 的“数据”中取出的，因此编译器不知道这些符号将采取的实际值（提示）。

让我们看看这些如何在导出的程序中体现出来：

class Foo(torch.nn.Module):
    def forward(self, x, y):
        a = x.item()
        b = y.tolist()
        return b + [a]

inps = (
    torch.tensor(1),
    torch.tensor([2, 3]),
)
ep = export(Foo(), inps)
print(ep)

结果是分配并返回了 3 个无符号符号（注意它们以“u”开头，而不是输入形状/有符号符号的常用“s”），1 个用于 item() 调用，以及每个 y 元素的 tolist() 调用。从范围约束字段中可以看出，这些符号的范围是 [-int_oo, int_oo] ，而不是分配给输入形状符号的默认 [0, int_oo] 范围，因为我们没有关于这些值的信息——它们不代表大小，因此不一定有正值。

守卫，torch._check() ¶

但上述情况很容易导出，因为这些符号的具体值在编译器决策中没有被使用；所有相关的是返回值是无符号符号。本节中突出显示的数据相关错误是以下情况，遇到了数据相关的守卫：

class Foo(torch.nn.Module):
    def forward(self, x, y):
        a = x.item()
        if a // 2 >= 5:
            return y + 2
        else:
            return y * 5

这里我们实际上需要“提示”，即 a 的具体值，以便编译器决定是否将 return y + 2 或 return y * 5 作为输出进行跟踪。因为我们使用 FakeTensors 进行跟踪，所以我们不知道 a // 2 >= 5 实际评估的结果是什么，导出错误时输出“无法在数据相关表达式 u0 // 2 >= 5 (unhinted) 上进行守卫”。

那么，我们如何导出这个玩具模型呢？与 torch.compile() 不同，导出需要完整的图编译，我们无法在这里进行图断开。以下是一些基本选项：

  1. 手动特殊化：我们可以通过选择要跟踪的分支来干预，要么通过删除控制流代码以仅包含特殊化分支，或者使用 torch.compiler.is_compiling() 在编译时保护要跟踪的内容。

  2. torch.cond() ：我们可以重写控制流代码以使用 torch.cond() ，这样我们就不在分支上进行特殊化。

虽然这些选项是有效的，但它们也有其缺陷。选项 1 有时需要彻底、侵入性的模型代码重写才能进行特殊化，而 torch.cond() 并不是一个处理数据相关错误的全面系统。正如我们将看到的，有些数据相关错误并不涉及控制流。

通常推荐的做法是从 torch._check() 调用开始。虽然这些调用给人的印象是纯粹是断言语句，但实际上它们是一个向编译器告知符号属性的系统。当 torch._check() 调用在运行时作为断言时，当在编译时跟踪时，检查的表达式会被发送到符号形状子系统进行推理，并且任何从表达式为真而得出的符号属性都会被存储为符号属性（前提是足够智能以推断这些属性）。因此，即使未支持的符号没有提示，如果我们能够通过 torch._check() 调用传达这些符号通常为真的属性，我们就可以潜在地绕过数据依赖性守卫，而无需重写有问题的模型代码。

例如，在上面的模型中，插入 torch._check(a >= 10) 会告诉编译器 y + 2 总是可以返回的，而 torch._check(a == 4) 则告诉它返回 y * 5 。看看我们重新导出这个模型会发生什么。

class Foo(torch.nn.Module):
    def forward(self, x, y):
        a = x.item()
        torch._check(a >= 10)
        torch._check(a <= 60)
        if a // 2 >= 5:
            return y + 2
        else:
            return y * 5

inps = (
    torch.tensor(32),
    torch.randn(4),
)
ep = export(Foo(), inps)
print(ep)

导出成功，并注意从范围约束字段中 u0 承担了 [10, 60] 的范围。

那么 torch._check() 调用实际上传达了哪些信息？这随着符号形状子系统变得更智能而变化，但在基本层面上，这些通常是正确的：

  1. 与非数据依赖表达式的等价性： torch._check() 调用传达等价性，如 u0 == s0 + 4 或 u0 == 5 。

  2. 范围细化：提供符号下限或上限的调用，如上所述。

  3. 关于更复杂表达式的某些基本推理：插入 torch._check(a < 4) 通常会让编译器知道 a >= 4 是错误的。对复杂表达式如 torch._check(a ** 2 - 3 * a <= 10) 的检查通常可以让你通过相同的守卫。

如前所述， torch._check() 的调用适用于数据依赖控制流之外。例如，这里有一个模型，其中 torch._check() 插入占主导地位，而手动特化和 torch.cond() 则没有：

class Foo(torch.nn.Module):
    def forward(self, x, y):
        a = x.item()
        return y[a]

inps = (
    torch.tensor(32),
    torch.randn(60),
)
try:
    export(Foo(), inps)
except Exception:
    tb.print_exc()

在这里， torch._check() 插入仅为了防止操作失败而需要。导出调用将失败，显示“无法在数据依赖表达式 -u0 > 60 上进行保护”，这意味着编译器不知道这是一个有效的索引操作 - 如果 x 的值超出了 y 的范围，则不是。在这里，手动特化过于限制， torch.cond() 没有位置。相反，通知编译器 u0 的范围就足够了：

class Foo(torch.nn.Module):
    def forward(self, x, y):
        a = x.item()
        torch._check(a >= 0)
        torch._check(a < y.shape[0])
        return y[a]

inps = (
    torch.tensor(32),
    torch.randn(60),
)
ep = export(Foo(), inps)
print(ep)

专用值

另一类数据依赖错误发生在程序在跟踪时尝试提取具体的数据依赖整数/浮点值。这看起来像“无法从数据依赖表达式提取特化整数”，这与前一类错误类似 - 如果在尝试评估具体的整数/浮点值时发生，则数据依赖守卫错误会在评估具体的布尔值时出现。

此错误通常发生在对数据依赖表达式进行显式或隐式的 int() 转换时。例如，这个列表推导式中的 range()调用隐式地对列表大小进行了 int() 转换：

class Foo(torch.nn.Module):
    def forward(self, x, y):
        a = x.item()
        b = torch.cat([y for y in range(a)], dim=0)
        return b + int(a)

inps = (
    torch.tensor(32),
    torch.randn(60),
)
try:
    export(Foo(), inps, strict=False)
except Exception:
    tb.print_exc()

对于这些错误，你可以尝试的一些基本选项包括：

  1. 避免不必要的 int() 转换调用，在这种情况下，返回语句中的 int(a) 。

  2. 使用 torch._check() 调用；不幸的是，在这种情况下，你可能只能进行特殊化（使用 torch._check(a == 60) ）。

  3. 在更高层次上重写有问题的代码。例如，列表推导在语义上相当于 repeat() 操作，不涉及 int() 类型转换。以下重写避免了数据依赖错误：

class Foo(torch.nn.Module):
    def forward(self, x, y):
        a = x.item()
        b = y.unsqueeze(0).repeat(a, 1)
        return b + a

inps = (
    torch.tensor(32),
    torch.randn(60),
)
ep = export(Foo(), inps, strict=False)
print(ep)

数据依赖错误可能更加复杂，您的工具箱中有许多选项可以处理它们： torch._check_is_size() 、 guard_size_oblivious() 或真实张量跟踪等。如需深入了解，请参阅导出编程模型或处理 GuardOnDataDependentSymNode 错误指南。

自定义操作

torch.export 可以导出具有自定义操作器的 PyTorch 程序。请参阅此页了解如何在 C++或 Python 中编写自定义操作器。

以下是一个在 Python 中注册自定义操作符的示例，以便由 torch.export 使用。需要注意的是，自定义操作符必须有一个 FakeTensor 内核。

@torch.library.custom_op("my_custom_library::custom_op", mutates_args={})
def custom_op(x: torch.Tensor) -> torch.Tensor:
    print("custom_op called!")
    return torch.relu(x)

@custom_op.register_fake
def custom_op_meta(x):
    # Returns an empty tensor with the same shape as the expected output
    return torch.empty_like(x)

下面是一个导出包含自定义操作符的程序示例。

class CustomOpExample(torch.nn.Module):
    def forward(self, x):
        x = torch.sin(x)
        x = torch.ops.my_custom_library.custom_op(x)
        x = torch.cos(x)
        return x

exported_custom_op_example = export(CustomOpExample(), (torch.randn(3, 3),))
print(exported_custom_op_example)
print(exported_custom_op_example.module()(torch.randn(3, 3)))

注意在 ExportedProgram 中，自定义操作符被包含在图中。

IR/分解

由 torch.export 生成的图仅包含 ATen 算子，它们是 PyTorch 的基本计算单元。由于 ATen 算子超过 3000 个，export 提供了一种根据某些特征缩小图中使用的算子集的方法，从而创建不同的中间表示（IR）。

默认情况下，export 生成最通用的 IR，其中包含所有 ATen 算子，包括功能算子和非功能算子。功能算子是指不包含任何输入突变或别名操作的算子。您可以在此处找到所有 ATen 算子的列表，并且可以通过检查 op._schema.is_mutable 来检查一个算子是否是功能算子，例如：

print(torch.ops.aten.add.Tensor._schema.is_mutable)
print(torch.ops.aten.add_.Tensor._schema.is_mutable)

这种通用 IR 可以用于在急切 PyTorch Autograd 中进行训练。通过 API torch.export.export_for_training 可以更明确地访问这种 IR，该 API 是在 PyTorch 2.5 中引入的，但调用 torch.export.export 在 PyTorch 2.6 中应产生相同的图。

class DecompExample(torch.nn.Module):
    def __init__(self) -> None:
        super().__init__()
        self.conv = torch.nn.Conv2d(1, 3, 1, 1)
        self.bn = torch.nn.BatchNorm2d(3)

    def forward(self, x):
        x = self.conv(x)
        x = self.bn(x)
        return (x,)

ep_for_training = torch.export.export_for_training(DecompExample(), (torch.randn(1, 1, 3, 3),))
print(ep_for_training.graph)

我们可以将这个导出的程序降低到只包含功能 ATen 算子的算子集，通过 API run_decompositions 实现将 ATen 算子分解为分解表中的指定算子，并将图功能化。通过指定空集，我们只进行功能化，不进行任何额外的分解。这导致包含约 2000 个算子的 IR（而不是上面的 3000 个算子），非常适合推理场景。

ep_for_inference = ep_for_training.run_decompositions(decomp_table={})
print(ep_for_inference.graph)

如我们所见，之前可变的算子 torch.ops.aten.add_.default 已被替换为 torch.ops.aten.add.default ，一个 l 算子。

我们还可以进一步将这个导出的程序降低到只包含核心 ATen 算子集的算子集，这是一个只包含约 180 个算子的集合。这个 IR 对于不想重新实现所有 ATen 算子的后端来说是最优的。

from torch.export import default_decompositions

core_aten_decomp_table = default_decompositions()
core_aten_ep = ep_for_training.run_decompositions(decomp_table=core_aten_decomp_table)
print(core_aten_ep.graph)

我们现在看到 torch.ops.aten.conv2d.default 已被分解为 torch.ops.aten.convolution.default 。这是因为 convolution 是一个更“核心”的算子，因为像 conv1d 和 conv2d 这样的操作可以使用相同的 op 实现。

我们还可以指定自己的分解行为：

my_decomp_table = torch.export.default_decompositions()

def my_awesome_custom_conv2d_function(x, weight, bias, stride=[1, 1], padding=[0, 0], dilation=[1, 1], groups=1):
    return 2 * torch.ops.aten.convolution(x, weight, bias, stride, padding, dilation, False, [0, 0], groups)

my_decomp_table[torch.ops.aten.conv2d.default] = my_awesome_custom_conv2d_function
my_ep = ep_for_training.run_decompositions(my_decomp_table)
print(my_ep.graph)

注意，现在 torch.ops.aten.conv2d.default 不是分解为 torch.ops.aten.convolution.default ，而是分解为 torch.ops.aten.convolution.default 和 torch.ops.aten.mul.Tensor ，这与我们的自定义分解规则相匹配。

导出数据库

torch.export 将始终从 PyTorch 程序中导出一个单一的计算图。由于这个要求，将会有一些 Python 或 PyTorch 特性与 torch.export 不兼容，这需要用户重写模型代码的一部分。我们在教程中已经看到了这样的例子——例如，使用 cond 重写 if 语句。

ExportDB 是记录支持和不支持的 Python/PyTorch 功能的标准参考，它本质上是一个程序示例列表，每个示例代表一个特定 Python/PyTorch 功能的用法及其与 torch.export 的交互。示例也被按类别标记，以便更容易搜索。

例如，让我们使用 ExportDB 来更好地理解 cond 运算符中的谓词是如何工作的。我们可以查看名为 cond_predicate 的示例，它有一个 torch.cond 标签。示例代码如下：

def cond_predicate(x):
    """
    The conditional statement (aka predicate) passed to ``cond()`` must be one of the following:
    - ``torch.Tensor`` with a single element
    - boolean expression
    NOTE: If the `pred` is test on a dim with batch size < 2, it will be specialized.
    """
    pred = x.dim() > 2 and x.shape[2] > 10
    return cond(pred, lambda x: x.cos(), lambda y: y.sin(), [x])

更一般地，当以下情况之一发生时，可以使用 ExportDB 作为参考：

  1. 在尝试 torch.export 之前，如果你事先知道你的模型使用了一些棘手的 Python/PyTorch 功能，并且你想知道 torch.export 是否覆盖了该功能。

  2. 尝试 torch.export 时，会出现失败，并且不清楚如何解决。

ExportDB 并不全面，但旨在涵盖典型 PyTorch 代码中找到的所有用例。如果您认为 ExportDB 应该添加或支持 torch.export 的某些重要的 Python/PyTorch 功能，请随时联系我们。

运行已导出的程序

由于 torch.export 只是一个图捕获机制，急切地调用 torch.export 生成的工件将等同于运行急切模块。为了优化导出程序的执行，我们可以通过 torch.compile 、AOTInductor 或 TensorRT 等后端将此导出工件传递过去。

class M(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.linear = torch.nn.Linear(3, 3)

    def forward(self, x):
        x = self.linear(x)
        return x

inp = torch.randn(2, 3, device="cuda")
m = M().to(device="cuda")
ep = torch.export.export(m, (inp,))

# Run it eagerly
res = ep.module()(inp)
print(res)

# Run it with torch.compile
res = torch.compile(ep.module(), backend="inductor")(inp)
print(res)

import torch._inductor

# Note: these APIs are subject to change
# Compile the exported program to a PT2 archive using ``AOTInductor``
with torch.no_grad():
    pt2_path = torch._inductor.aoti_compile_and_package(ep)

# Load and run the .so file in Python.
# To load and run it in a C++ environment, see:
# https://pytorch.org/docs/main/torch.compiler_aot_inductor.html
aoti_compiled = torch._inductor.aoti_load_package(pt2_path)
res = aoti_compiled(inp)

我们引入了 torch.export ，这是 PyTorch 2.X 版本中从 PyTorch 程序中导出单个计算图的新方法。特别是，我们展示了为了导出图，需要进行的几个代码修改和考虑（控制流操作、约束等）。
