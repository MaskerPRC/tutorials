（原型）用于调试停滞作业的飞行记录器 ¶


创建于：2025 年 4 月 1 日 | 最后更新：2025 年 4 月 1 日 | 最后验证：2024 年 9 月 9 日

作者：Chirag Pandya, Junjie Wang

你将学到什么

  • 了解一种用于在分布式训练期间调试停滞作业的新工具。

  • 学习如何启用此工具并使用收集到的数据来分析停滞作业。

前提条件 ＿

  • PyTorch 版本 2.5 或更高版本。

  • tabulate. 您可以通过运行 pip install tabulate 来安装。

概述 ¶

人工智能分布式训练任务是指使用网络中连接的多个设备（如 GPU 或 CPU）训练机器学习模型的过程。这种方法允许更快、更高效地训练需要大量计算资源的大型模型。工程师的目标是尽可能快地完成人工智能训练任务，并持续改进，以便后续训练可以更快地进行。一个训练好的、可用的模型是最终期望的结果。完成训练的最大障碍之一是“停滞任务”的概念。

当分布式人工智能训练任务停止在较长时间内做出有意义进展时，被认为是停滞的。

一个任务可能因为各种原因而停滞：

  • 数据饥饿：当训练作业没有以预期的速率接收数据时，这可能是由于数据管道或数据源的问题。

  • 资源限制：如果运行作业的系统没有足够的计算资源（如 CPU、GPU 或内存），作业可能无法继续进行。

  • 网络问题：在分布式训练设置中，模型的不同部分或数据可能在不同设备上处理。如果存在网络问题，这些设备之间的通信可能会中断，导致作业卡住。

  • 软件错误或异常：训练代码或底层库和框架中的错误也可能导致作业卡住。

  • 同步问题：在分布式训练中，计算的不同部分通常并行运行，并在某些点需要同步。如果同步失败，作业可能会卡住。例如，如果一个或多个进程未能加入集体操作，而其他进程已经加入，则可能导致死锁。这会导致作业无法继续进行。

如其名所示，飞行记录器在集体操作运行时捕获诊断信息。捕获的诊断信息用于帮助识别作业卡住时的根本原因。飞行记录器由两个核心部分组成：

  • 收集部分：当启用时，集体操作的信息将记录在内存中的环形缓冲区中。在作业超时或按需时，内存缓冲区可以被检索或转储到文件中。

  • 工具/飞行记录器目录中提供了一个分析脚本（详细信息见下文）。


    分析脚本使用收集到的数据运行已知启发式方法，并尝试自动识别导致作业停滞的根本问题。

启用飞行记录器 ¶

要使飞行记录器的初始版本工作，需要三个环境变量。

  • TORCH_NCCL_TRACE_BUFFER_SIZE = (0, N) 将 N 设置为正数可以启用收集。 N 代表将在环形缓冲区内部保留的条目数。我们建议将此值设置为 2000。默认值为 2000 。

  • TORCH_NCCL_DUMP_ON_TIMEOUT = (true, false) 将此设置为 true 将在作业超时时将诊断文件写入磁盘。如果启用，每个 rank 的输出将有一个文件在作业的运行目录中。默认值为 false 。

  • TORCH_NCCL_DEBUG_INFO_TEMP_FILE 将飞行记录器输出文件的路径和文件前缀设置。每个 rank 一个文件。默认值为 /tmp/nccl_trace_rank_ 。

可选设置：

  • TORCH_NCCL_TRACE_CPP_STACK = (true, false) 将此设置为 true 将启用在飞行记录器中捕获 C++堆栈跟踪。C++堆栈跟踪在提供从 PyTorch Python 调用到原始 C++实现的精确代码路径时非常有用。另见 TORCH_SYMBOLIZE_MODE 中的附加设置。

  • TORCH_NCCL_ENABLE_TIMING = (true, false) : 将此设置为 true 将启用每个集体操作开始时的额外 CUDA 事件，并记录每个集体操作的持续时间。这可能会产生一些 CPU 开销。在收集的数据中，持续时间字段表示每个集体操作执行所需的时间。

其他设置 ¶

  • TORCH_SYMBOLIZE_MODE = (dladdr, addr2line, fast) : 此设置确定用于从运行程序检索 C++跟踪的程序。


    默认设置为 addr2line 。

    fast 是一种新的实验模式，显示其速度比传统的 addr2line 快得多。使用此设置与 TORCH_NCCL_TRACE_CPP_STACK 结合，以在飞行记录器数据中收集 C++ 跟踪信息。

  • 如果您不想将飞行记录器数据导出到本地磁盘，而是导出到自己的存储，您可以定义自己的写入类。这个类应该继承自类 ::c10d::DebugInfoWriter （代码），然后使用 ::c10d::DebugInfoWriter::registerWriter （代码）注册新的写入器，在我们启动 PyTorch 分布式之前。

通过 API 检索飞行记录仪数据

您也可以通过 API 调用来获取飞行记录器数据。以下展示了使用默认参数的 API：

torch._C._distributed_c10d._dump_nccl_trace(includeCollectives=True, includeStackTraces=True, onlyActive=False)

查看数据，您可以按照以下示例 unpickle ：

t = pickle.loads(torch._C._distributed_c10d._dump_nccl_trace())
print(t)

分析飞行记录仪转储

在 pytorch/tools/flight_recorder 目录中提供了方便的脚本，用于分析捕获的数据。

要运行便利脚本，请按照以下步骤操作：

  1. 将一个 rank 的所有文件复制到一个单独的目录中。

  2. 运行脚本，请使用以下命令：

python fr_trace.py <dump dir containing trace files> [-o <output file>]

如果您安装了 PyTorch 的夜间构建或使用 USE_DISTRIBUTED=1 从头构建，您可以直接使用以下命令：

torchfrtrace <dump dir containing trace files> [-o <output file>]

目前，我们支持两种分析脚本模式。第一种模式允许脚本对解析的飞行记录器转储应用一些启发式方法，以生成报告，识别超时潜在原因。第二种模式仅输出原始转储。默认情况下，脚本打印所有 rank 和所有“进程组”(PGs)的飞行记录器转储。可以使用–selected-ranks 参数缩小到特定的 rank，以及使用–pg-filters 参数缩小到 PGs。一个示例命令是：

注意：需要 tabulate 模块，因此您可能需要先使用 pip 安装它。

python fr_trace.py <dump dir containing trace files> -j [--selected-ranks i j k ...] [--pg-filters tp dp]
torchfrtrace <dump dir containing trace files> -j [--selected-ranks i j k ...] [--pg-filters 0 2]

一个端到端示例

为了演示飞行记录器的使用，我们将使用一个小程序来诱导不匹配的集体。在这个例子中， rank0 被编程执行额外的集体操作。飞行记录器的转储文件保存到 /tmp 目录下。出于演示目的，我们把这个程序命名为 crash.py 。

备注

请注意，这是一个简化的例子。在现实世界的场景中，这个过程将涉及更多的复杂性。

import torch
import torch.distributed as dist
import os
from datetime import timedelta

local_rank = int(os.environ["LOCAL_RANK"])
world_size = int(os.environ["WORLD_SIZE"])
assert world_size <= 8, "world size must be less than or equal to 8"
os.environ["TORCH_NCCL_DEBUG_INFO_TEMP_FILE"] = "/tmp/trace_"
os.environ["TORCH_NCCL_DUMP_ON_TIMEOUT"] = "1"
os.environ["TORCH_NCCL_TRACE_BUFFER_SIZE"] = "2000"
device = torch.device(f"cuda:{local_rank}")
print(f"{local_rank=} {world_size=} master addr: {os.environ['MASTER_ADDR']} master port: {os.environ['MASTER_PORT']} {device=}")

# Initialize the process group with a small timeout so that jobs fail quickly
dist.init_process_group("nccl", world_size=world_size, rank=local_rank, timeout=timedelta(seconds=1))

a = torch.full((3, 4), float(local_rank), device=device)
# Write some collectives to populate Flight Recorder data
for i in range(2):
  print(f"calling allreduce on {local_rank=}")
  f = dist.all_reduce(a)

# rank0 is doing an additional collective
if local_rank == 0:
  print("rank0 is doing an allreduce on tensor b, but other ranks forgot")
  b = torch.full((4,5), float(local_rank), device=device)
  f = dist.all_reduce(b)

for i in range(2):
  print(f"calling allreduce on {local_rank=}")
  f = dist.all_reduce(a)

torch.cuda.synchronize(device=device)
print(f"{local_rank=} exiting")

要运行此程序，请使用 torchrun :

torchrun --nnodes=1 --nproc_per_node=2 crash.py

你应该在 /tmp 目录下看到两个文件：

$ls /tmp/trace*
# Expected output
/tmp/trace_0 /tmp/trace_1

最后，为了分析这两个文件，我们使用 torchfrtrace 命令：

torchfrtrace --prefix "trace_" /tmp/

跟踪命令的输出旨在易于阅读。它包括导致失败的一组集体信息。上述命令的输出如下所示。我们可以清楚地看到 rank 1 没有加入“all_reduce”集体。

结论 ¶

在本教程中，我们了解了一个名为 Flight Recorder 的新 PyTorch 诊断工具。我们讨论了如何启用 Flight Recorder 从机器收集诊断数据。此外，我们还探讨了如何使用 PyTorch 仓库 tools/flight_recorder 目录中的便利脚本来分析从 Flight Recorder 捕获的数据。
