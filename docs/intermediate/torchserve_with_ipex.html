通用矩阵乘法（GEMM） 在融合乘加（FMA）或点积（DP）执行单元上运行，当启用超线程时，将导致瓶颈并造成线程等待/ 在同步屏障处旋转延迟，因为使用逻辑核心会导致所有工作线程的并发性不足，因为每个逻辑线程/ 争夺相同的核心资源 。相反，如果我们每个物理核心使用一个线程，我们就可以避免这种竞争。因此，我们通常建议通过设置 CPU/ 线程亲和性到物理核心/ 核心固定来避免使用逻辑核心。

多插槽系统具有非一致性内存访问（NUMA），这是一种共享内存架构，描述了主内存模块相对于处理器的放置。但如果一个进程不是 NUMA 感知的，当远程内存在运行时通过英特尔超路径互连（UPI） 跨插槽迁移时，就会频繁访问慢速的远程内存。我们通过设置 CPU 线程亲和性到特定的插槽，通过核心绑定来解决这个问题。

了解这些原则，适当的 CPU 运行时配置可以显著提高即插即用性能。

在这篇博客中，我们将向您介绍您应该了解的重要运行时配置，从 CPU 性能调整指南中解释它们的工作原理，如何进行性能分析以及如何通过我们内置的简单启动脚本将它们集成到模型服务框架如 TorchServe 中。

我们将用视觉方式解释这些想法 直观地 从 基本原理 出发，结合众多 配置文件 ，向您展示我们如何将所学应用于使 TorchServe 的 CPU 性能更出色。

  1. 该功能必须通过在 config.properties 中设置 cpu_launcher_enable=true 来显式启用。

避免逻辑核心进行深度学习 ¶

避免逻辑核心进行深度学习工作负载通常可以提高性能。为了理解这一点，让我们回顾一下 GEMM。

优化 GEMM 优化深度学习

深度学习训练或推理的大部分时间都花在了数百万次的 GEMM 重复操作上，而 GEMM 是全连接层的核心。全连接层自多层感知器（MLP） 被证明是任何连续函数的通用逼近器以来已经使用了数十年。任何 MLP 都可以完全表示为 GEMM。甚至通过使用 Toepliz 矩阵 ，卷积也可以表示为 GEMM。

回到原始主题，大多数 GEMM 算子从使用非超线程中受益，因为在深度学习训练或推理的大部分时间都花在了数百万次的 GEMM 重复操作上，这些操作运行在由超线程核心共享的融合乘加（FMA）或点积（DP）执行单元上。启用超线程时，OpenMP 线程将争夺相同的 GEMM 执行单元。

如果两个逻辑线程同时运行 GEMM，它们将共享相同的核心资源，导致前端绑定，从而使这种前端绑定的开销大于同时运行两个逻辑线程的收益。

因此，我们通常建议避免使用逻辑核心进行深度学习工作负载以获得良好的性能。启动脚本默认仅使用物理核心；然而，用户可以通过简单地切换启动脚本中的 --use_logical_core 旋钮来轻松地实验逻辑核心与物理核心。

练习

我们将使用以下示例来演示向 ResNet50 输入虚拟张量：

import torch
import torchvision.models as models
import time

model = models.resnet50(pretrained=False)
model.eval()
data = torch.rand(1, 3, 224, 224)

# warm up
for _ in range(100):
    model(data)

start = time.time()
for _ in range(100):
    model(data)
end = time.time()
print('Inference took {:.2f} ms in average'.format((end-start)/100*1000))

在本博客中，我们将使用英特尔® VTune™ 分析器进行性能分析和验证优化。所有练习将在配备两颗英特尔(R) Xeon(R) Platinum 8180M CPU 的机器上运行。CPU 信息如图 2.1 所示。

环境变量 OMP_NUM_THREADS 用于设置并行区域的线程数。我们将比较 OMP_NUM_THREADS=2 与（1）使用逻辑核心和（2）仅使用物理核心。

  1. 两个 OpenMP 线程试图利用超线程核心（0，56）共享的同一组 GEMM 执行单元。

我们可以通过在 Linux 上运行 htop 命令来可视化这一点，如下所示。

我们注意到 Spin Time 被标记，不平衡或串行自旋导致了其中大部分 - 总计 8.982 秒中的 4.980 秒。使用逻辑核心时的不平衡或串行自旋是由于工作线程的并发不足，因为每个逻辑线程都在争夺相同的核心资源。

执行摘要中的“热点区域”部分显示，__kmp_fork_barrier 消耗了 4.589 秒的 CPU 时间 - 在 9.33%的 CPU 执行时间内，线程因线程同步在此屏障处空转。

  1. 每个 OpenMP 线程在各自的物理核心（0，1）中利用 GEMM 执行单元。

我们首先注意到，通过避免使用逻辑核心，执行时间从32秒降低到23秒。虽然仍然存在一些不可忽视的不平衡或串行空转，但我们注意到相对改进从4.980秒到3.887秒。

通过不使用逻辑线程（而是每个物理核心使用一个线程），我们避免了逻辑线程争夺相同的核心资源。热点区域部分也显示，__kmp_fork_barrier 的时间相对改进从 4.589 秒到 3.530 秒。

本地内存访问总是比远程内存访问快 ¶

我们通常建议将进程绑定到本地套接字，这样进程就不会跨越套接字迁移。这样做的一般目的是利用本地内存上的高速缓存，并避免远程内存访问，这可能会慢2倍左右。

图1. 双路配置

图 1. 展示了一个典型的双路配置。请注意，每个套接字都有自己的本地内存。套接字通过英特尔超路径互连（UPI）相互连接，允许每个套接字访问另一个套接字的本地内存，称为远程内存。本地内存访问总是比远程内存访问快。

图 2.1. CPU 信息

用户可以通过在 Linux 机器上运行 lscpu 命令来获取他们的 CPU 信息。图 2.1.展示了在一个具有两个 Intel(R) Xeon(R) Platinum 8180M CPU 的机器上执行 lscpu 的示例。注意，每个插槽有 28 个核心，每个核心有 2 个线程（即启用了超线程）。换句话说，除了 28 个物理核心外，还有 28 个逻辑核心，每个插槽总共 56 个核心。并且有 2 个插槽，总共 112 个核心（ 线程 每 核心 x 核心 每 插槽 x 插槽 ）。

图 2.2. CPU 信息

2 个插座分别映射到 2 个 NUMA 节点（NUMA 节点 0，NUMA 节点 1）。物理核心的索引先于逻辑核心。如图 2.2 所示，第一个插座上的前 28 个物理核心（0-27）和前 28 个逻辑核心（56-83）位于 NUMA 节点 0。第二个插座上的后 28 个物理核心（28-55）和后 28 个逻辑核心（84-111）位于 NUMA 节点 1。同一插座上的核心共享本地内存和最后一级缓存（LLC），这比通过英特尔 UPI 的跨插座通信要快得多。

现在我们已经了解了 NUMA、跨插座（UPI）流量、多处理器系统中的本地与远程内存访问，让我们来分析和验证我们的理解。

使用核心绑定实现多工作线程推理的 CPU 高效使用 ¶

在运行多工作线程推理时，核心被工作线程重叠（或共享），导致 CPU 使用效率低下。为了解决这个问题，启动脚本将可用的核心数平均分配给工作线程，使得每个工作线程在运行时被绑定到指定的核心。

TorchServe 练习

在这个练习中，让我们将我们之前讨论过的 CPU 性能调整原则和建议应用到 TorchServe apache-bench 基准测试 。

我们将使用 ResNet50，4 个工作线程，并发 100，请求数量 10,000。所有其他参数（例如，batch_size、input 等）与默认参数相同。

我们将比较以下三个配置：

  1. 默认 TorchServe 设置（无核心绑定）

  2. torch.set_num_threads = number of physical cores / number of workers （无核心绑定）

  3. 通过启动脚本进行核心固定（必需 Torchserve>=0.6.1）

在这个练习之后，我们将验证我们更喜欢避免逻辑核心，并更喜欢通过核心固定使用本地内存访问，以实际的 TorchServe 用例为例。

1. 默认 TorchServe 设置（无核心固定）¶

base_handler 没有显式设置 torch.set_num_threads。因此，默认的线程数是物理 CPU 核心的数量，如此处所述。用户可以通过 base_handler 中的 torch.get_num_threads 检查线程数。每个 4 个主要工作线程启动一个物理核心编号（56）的线程，总共启动 56x4 = 224 个线程，这比核心总数 112 多。因此，核心保证会高度重叠，逻辑核心利用率高——多个工作线程同时使用多个核心。此外，由于线程没有绑定到特定的 CPU 核心，操作系统会定期调度线程到位于不同插槽的核心。

  1. CPU 使用率

启动了4个主要工作线程，然后每个线程在所有核心上启动了物理核心数（56）的线程，包括逻辑核心。

  1. 核绑定停顿

我们观察到非常高的核绑定停顿率为 88.4%，降低了流水线效率。核绑定停顿表明 CPU 中可用执行单元的使用不理想。例如，连续的几个 GEMM 指令可能因为超线程核心共享的融合乘加（FMA）或点积（DP）执行单元而引起核绑定停顿。正如前文所述，使用逻辑核心会放大这个问题。

空的流水线槽位未填充微操作（uOps）会被认为是停顿。例如，如果没有核心固定，CPU 的使用可能不会有效地用于计算，而是用于其他操作，如 Linux 内核的线程调度。上面我们看到，__sched_yield 导致了大部分的自旋时间。

  1. 线程迁移

没有核心固定时，调度器可能会将运行在某个核心上的线程迁移到另一个核心。线程迁移可能会导致线程与已经加载到缓存中的数据解关联，从而增加数据访问的延迟。在 NUMA 系统中，当线程跨越插槽迁移时，这个问题会加剧。现在被加载到本地内存的高速缓存中的数据变成了远程内存，这要慢得多。

通常线程的总数应该小于或等于核心支持的线程总数。在上面的例子中，我们注意到在 core_51 上执行了大量的线程，而不是预期的 2 个线程（因为 Intel(R) Xeon(R) Platinum 8180 CPU 启用了超线程）。这表明发生了线程迁移。

此外，请注意线程（TID:97097）在大量 CPU 核心上执行，表明 CPU 迁移。例如，此线程在 cpu_81 上执行，然后迁移到 cpu_14，然后迁移到 cpu_5，依此类推。此外，请注意此线程在多个节点间来回迁移，导致内存访问效率非常低。例如，此线程在 cpu_70（NUMA 节点 0）上执行，然后迁移到 cpu_100（NUMA 节点 1），然后迁移到 cpu_24（NUMA 节点 0）。

  1. 非均匀内存访问分析

比较本地与远程内存访问随时间的变化。我们观察到大约一半，即 51.09%的内存访问是远程访问，表明 NUMA 配置不理想。

2. torch.set_num_threads = number of physical cores / number of workers (无核心绑定)¶

与启动器的核心绑定进行苹果对苹果的比较时，我们将线程数设置为核心数除以工作线程数（启动器内部会这样做）。在 base_handler 中添加以下代码片段：

torch.set_num_threads(num_physical_cores/num_workers)

如前所述，没有核心绑定，这些线程没有绑定到特定的 CPU 核心，导致操作系统定期在不同的插槽上调度线程。

  1. CPU 使用率

启动了4个主要工作线程，然后每个线程在所有核心上（包括逻辑核心）启动了 num_physical_cores/num_workers 个线程（14个线程）。

  1. 核绑定停滞

尽管核绑定停滞的百分比从88.4%下降到73.5%，但核绑定仍然非常高。

  1. 线程迁移

与之前相似，没有核心固定线程（TID:94290）在大量 CPU 核心上执行，表明 CPU 迁移。我们再次注意到跨插槽线程迁移，导致内存访问非常低效。例如，此线程在 cpu_78（NUMA 节点 0）上执行，然后迁移到 cpu_108（NUMA 节点 1）。

  1. 非均匀内存访问分析

尽管比原始的 51.09%有所改进，但仍有 40.45%的内存访问是远程的，表明 NUMA 配置不理想。

3. 启动器核心绑定 ¶

启动器将内部平均分配物理核心给工作进程，并将它们绑定到每个工作进程。提醒一下，启动器默认只使用物理核心。在这个例子中，启动器将工作进程 0 绑定到核心 0-13（NUMA 节点 0），工作进程 1 绑定到核心 14-27（NUMA 节点 0），工作进程 2 绑定到核心 28-41（NUMA 节点 1），工作进程 3 绑定到核心 42-55（NUMA 节点 1）。这样做确保了核心在工作进程之间不会重叠，并避免了逻辑核心的使用。

  1. CPU 使用率

启动了4个主要工作线程，然后每个线程又启动了 num_physical_cores/num_workers 个（14个）绑定到分配的物理核心的线程。

  1. 核绑定停顿

核绑定停顿从原始的88.4%显著降低到46.2% - 几乎是2倍的性能提升。

我们验证，使用核心绑定，大部分 CPU 时间被有效地用于计算 - 旋转时间为 0.256 秒。

  1. 线程迁移

我们验证，OMP 主线程#0 被绑定到指定的物理核心（42-55），并且没有跨插槽迁移。

  1. 非均匀内存访问分析

现在几乎所有，89.52%，的内存访问都是局部访问。

结论 ¶

在这篇博客中，我们展示了正确设置 CPU 运行时配置可以显著提升 CPU 的出厂性能。

我们已经介绍了一些通用的 CPU 性能调优原则和建议：

  • 在启用超线程的系统上，通过设置线程亲和性到物理核心来避免使用逻辑核心。

  • 在具有 NUMA 的多插槽系统中，通过设置线程亲和性到特定插槽，避免跨插槽远程内存访问。

我们从第一性原理出发对这些想法进行了可视化解释，并通过性能分析验证了性能提升。最后，我们将所学知识应用于 TorchServe，以提升 TorchServe 的 CPU 性能。

这些原则可以通过一个易于使用的启动脚本自动配置，该脚本已集成到 TorchServe 中。
